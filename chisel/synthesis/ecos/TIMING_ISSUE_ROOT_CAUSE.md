# 时序问题根本原因分析

## 🔍 问题确认

触发器延迟显示为 27.593 ns 的**根本原因已找到**！

## 根本原因

### ⚠️ 时钟网络扇出过大，没有缓冲器

**关键数据**：
- **时钟扇出**：**25,556 个触发器**
- **时钟网络**：直接连接，无缓冲器
- **时钟延迟**：被标记为 "ideal"（理想网络）

```
sys_clk_i_pad → [PAD] → sys_clk → 25,556 个触发器
                                   ↑
                            没有时钟树！
```

## 详细分析

### 1. 时钟网络结构

**当前状态**：
```verilog
// 所有 25,556 个触发器直接连接到 sys_clk
DFFQX1H7L _161209_ (.CK(sys_clk), ...);
DFFQX1H7L _161210_ (.CK(sys_clk), ...);
DFFQX1H7L _161211_ (.CK(sys_clk), ...);
// ... 25,553 more
```

**问题**：
- 单个时钟网络驱动 25,556 个负载
- 没有时钟缓冲器（Clock Buffer）
- 没有时钟树结构（Clock Tree）
- 巨大的电容负载导致延迟

### 2. 为什么延迟是 27.593 ns

**物理原因**：
1. **RC 延迟**：
   - 25,556 个触发器的输入电容
   - 长距离的时钟线电阻
   - RC = R × C ≈ 27 ns

2. **扇出延迟**：
   - 单个驱动器无法快速驱动这么多负载
   - 信号转换时间（slew）变慢

3. **OpenSTA 的处理**：
   - 时钟网络标记为 "ideal"
   - 实际的网络延迟被算在触发器的 CK→Q 上
   - 这就是为什么看到 27.593 ns

### 3. 正常的时钟树应该是什么样

**应该有的结构**：
```
sys_clk_i_pad → [PAD] → sys_clk_root
                           ↓
                    [Clock Buffer Level 1]
                    ↙     ↓     ↘
              [Buf]   [Buf]   [Buf]
               ↓       ↓       ↓
            [Level 2 Buffers...]
               ↓       ↓       ↓
            触发器  触发器  触发器
            (每组 ~100 个)
```

**好处**：
- 平衡延迟
- 减少扇出
- 控制 skew
- 总延迟 < 1 ns

## 解决方案

### 方案 1：时钟树综合 (CTS) ⭐ 推荐

**工具**：
- OpenROAD (TritonCTS)
- iEDA (iCTS)

**步骤**：
1. 完成布局（Placement）
2. 运行 CTS
3. 插入时钟缓冲器
4. 平衡时钟树
5. 重新运行 STA

**预期结果**：
- 时钟网络延迟：< 1 ns
- 时钟 skew：< 0.1 ns
- 实际逻辑延迟：~10 ns
- **可以达到 100MHz**

### 方案 2：手动插入时钟缓冲器

**在综合时**：
```tcl
# Yosys 综合脚本
set_max_fanout 16 [get_nets sys_clk]
insert_buffer -max_fanout 16 [get_nets sys_clk]
```

**问题**：
- Yosys 的时钟树综合能力有限
- 可能需要手动调整

### 方案 3：降低频率（临时）

**如果无法进行 CTS**：
- 降低到 30-40 MHz
- 给时钟网络更多时间稳定
